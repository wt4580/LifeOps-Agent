# 求职展示：把项目讲成可验证的工程案例

## 项目定位

面向个人任务管理的 AI 应用，核心是把自然语言请求转换成受约束、可确认、可追溯的数据库操作。技术栈为 FastAPI、LangGraph、SQLite、Qwen 兼容接口；SSE 提供过程事件与增量文本。

适合展示的三个工程决策：

1. **写操作确认**：待办先生成草案，修改、取消和确认通过 checkpoint 继续执行；现有账户余额修改也要求确认。用数据库前后状态说明边界，而非只展示聊天文本。
2. **执行约束**：前台/后台独立预算、LLM 和工具拦截、只读 SQL 的会话作用域、执行摘要与审计。供应商缺少 usage 时保守预留预算；不把预留值当成实际 token 费用。
3. **交付与回归**：多阶段非 root 镜像、专用数据卷、健康检查、kind 单副本部署、JUnit 和契约报告。Jenkinsfile 与 GitHub CI 已提供，实际远端构建状态需以运行记录为准。

## 三分钟演示

启动 Compose，登录演示账号，说明规则模拟模型只用于低成本体验工程链路。

输入「明天下午3点开会」，展示草案与数据库尚未写入；输入「可以改成后天吗」，观察日期更新，随后取消。再创建并确认一次，在待办列表验证日期和记录数。问「报销需要哪些材料」，打开来源，指出是仓库内虚构制度。最后展示 trace 的 harness_summary、测试报告和 kind 的就绪 Pod。

普通文本聊天可提供建议；语音、真实天气、长期学习和向量检索不属于离线演示的效果声明。实际模型能力应另外用真实供应商和保留集验证。

## 验证结果与口径

2026-10-27 验证：Linux 容器中 285 项单元测试通过、100/100 条流程契约通过；Docker / kind 部署均通过 HTTP 冒烟。详见[流程报告](../app/eval/reports/e2e-contract.md)与[逐例 JSON](../app/eval/reports/e2e-contract.json)，JUnit XML 归档于本地 `artifacts/unit.xml`。报告含测试源码 SHA-256；后续修改应重新运行，不能仅根据本文判定新分支仍全部通过。

场景包括待办确认、取消、修改、多日期、历史消费记账、账户变更确认、RAG 引用、跨作用域工具拦截、预算耗尽和模拟供应商失败。样例规模是 10 类 × 10 变体。它检验程序行为，并不测量真实模型任务成功率、幻觉率或网络负载性能。

本轮没有调用付费模型，也未重新运行 README 中依赖个人外部语料的历史检索指标。应避免把历史 Recall@1 和合成契约通过率合并为一个“准确率”。

## 可以用于简历的事实

> 开发基于 FastAPI / LangGraph 的个人事务 Agent，实现 SSE、多轮任务编排、HITL 确认和 RAG 来源追溯；为模型与工具执行加入预算、会话隔离和审计；提供 Docker 多阶段镜像、Jenkins 流水线与 kind 部署，并建立 100 条合成端到端流程契约。

如果还没有在 Jenkins 上触发成功构建，不要写“已实现 Jenkins 自动发布上线”；真实模型评测完成前，不写虚构的准确率、降本比例或吞吐量。面试时可现场复跑报告，展示失败用例如何定位。

## 下一阶段最有价值的工作

优先补真实模型保留集：表达变体、歧义、否定、跨任务对话、工具错误与知识库无答案。按类型分析成功率、真实 token、首字延迟与总延迟。RAG 对比需要固定语料、模型、候选数和日期，单独比较 BM25、向量、混合、混合加重排；目前不能声称某组件带来已验证的增益。

然后拆分工具注册和参数 schema，减少 graph_chat 中分派逻辑的耦合；为客户端重试和跨进程并发建立数据库级幂等键；把可恢复与不可恢复工具错误区分展示。扩容时再迁移 PostgreSQL、外部 checkpoint 与分布式会话协调。当前 SQLite、内存队列和单副本限制应能清楚解释。
